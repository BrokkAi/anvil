<section class="home-section">
  <p class="section-label">A deliberate boundary</p>
  <h2>Build the experience. Keep the runtime independent.</h2>
  <p>
    ACP keeps the client experience independent from the runtime implementation. Editors and bots
    stay focused on interaction while Anvil provides consistent execution semantics behind a
    separate process.
  </p>

  <div class="ownership-grid">
    <article>
      <small>CLIENT OWNS</small>
      <h3>The experience</h3>
      <ul>
        <li>Conversation and task UI</li>
        <li>Permission prompts</li>
        <li>Session controls</li>
        <li>Streaming presentation</li>
      </ul>
    </article>
    <article>
      <small>ANVIL OWNS</small>
      <h3>The agent runtime</h3>
      <ul>
        <li>Model routing and tool loop</li>
        <li>Permission enforcement</li>
        <li>Sessions and context compaction</li>
        <li>Sandboxing and MCP servers</li>
      </ul>
    </article>
  </div>
</section>

<section class="home-section">
  <div class="replaceability-panel">
    <div>
      <p class="section-label">Replaceable by design</p>
      <h2>Change the engine without rebuilding the cockpit.</h2>
      <p>
        Because Anvil is an ACP subprocess, a client can point at an official release, a locally
        built fork, or another compatible executable. Runtime and interface can evolve on separate
        release cycles while the process boundary stays explicit.
      </p>
    </div>
    <aside>
      <small>ARCHITECTURE × LICENSE</small>
      <h3>A practical path to user freedom</h3>
      <p>
        ACP is an architectural choice, not an LGPL requirement. But the replaceable executable
        boundary complements the LGPL freedoms in the Anvil component: recipients can inspect,
        modify, rebuild, and run their version without needing the client to relink against it.
      </p>
